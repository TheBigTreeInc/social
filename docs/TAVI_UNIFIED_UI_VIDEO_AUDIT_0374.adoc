== Purpose and evidentiary boundary

This document analyses the operator-supplied ~49-second, 362x668 screen recording `Screen Recording 2026-10-20 184905.mp4` and compares visible behaviour with the *0.3.73 ZipRunner source*. Tavi is a messenger first. Atrium, Life, Companion, Wallet and other optional experiences must never trap the user away from Home or conceal messaging. The video is of a compact desktop Tavi window; it does **not** prove actual Android behaviour, server availability, acceptance of any hosted game or dark-theme rendering. Time ranges below are approximate.

=== Additional confirmed constraints

* On Windows, conversations may open as separate native Tauri WebViews; Android/Web use one compact WebView. Shared components must support both without copying sessions into child windows.
* Extension iframes are `sandbox="allow-scripts"`, without `allow-same-origin` and without any Social bearer. The design-system project must not weaken this.
* The operator previously requested that Games stay optional and use the Home dock, App Store updates surface as a notification, contacts sort alphabetically, and themes include light green and dark green. Preserve those decisions.
* The GitHub cross-repository validation/registration workflow and local package cache have been deferred; do not conflate them with the UI work.
* Some historical workboard acceptance checks explicitly require roster Search, My Games, and the old toolbar. Those contradict the newer operator direction. Keep their original recorded criteria and add an explicit supersession note; never silently edit or mark them Done.

== Framework decision: Lit components + CSS tokens, introduced incrementally

Recommend **Lit (standards-based Web Components)** with a small Tavi-owned TypeScript or JavaScript component library and CSS custom-property design tokens. Keep Vite, Tauri, the canonical browser SDK, and LoopRD untouched initially. Start without a dependency for 0.3.74; prototype Lit components behind existing HTML rendering on a later pass.

Why Lit rather than replacing the app with a full React/Vue rewrite:

* Small components can be extracted one at a time from today's template strings; no parallel permanent UI rewrite or new state manager is required.
* Native custom elements run in the existing Chromium/WebView2 and Android WebView runtimes and ordinary browsers. Framework compatibility still requires testing against Tauri versions and the SDK.
* Shadow DOM encapsulates component structure and rules. Theme variables are passed deliberately to the host; external sandboxed iframe styling remains independent.
* Existing state can be adapted to reactive properties. Prefer explicit app-owned state and thin services instead of putting business logic in view components.
* Keep classic MSN-style green typography, borders and chrome as tokens rather than adopting a generic mobile material-design look.

Alternatives: Vue or React are reasonable for a new app, but migrating the ~133 KB central view file and associated imperative lifecycle all at once is higher risk. A large ready-made widget library may introduce styles, bundle weight and opinionated navigation inconsistent with compact Tavi. Reassess after an isolated proof-of-concept and bundle/performance measurements.

=== Ownership contract

* Host owns chrome, Home/back/minimize navigation, dialogs requesting permissions, account context, global notifications and update badges.
* Messenger owns contact and conversation presentation, drafts, unread, presence, native windows and service calls.
* Publishers own their application content and may choose to use the optional Tavi UI tokens / SDK, but may not reach into host DOM or inherit credentials. Host `host.info` signals embedded-mode and host-managed navigation. Hide an extension's redundant Return affordance *only after an authenticated bridge exchange*; otherwise leave publisher navigation intact.
* A publisher can scroll inside its own view; the host provides a single bounded viewport. Avoid two independently scrolling containers around the same content.

=== Design tokens

Introduce a versioned set of semantic CSS variables instead of changing hex values ad hoc:

* Color: `--tavi-surface`, `--tavi-surface-raised`, `--tavi-chrome`, `--tavi-accent`, `--tavi-text`, `--tavi-text-muted`, `--tavi-border`, `--tavi-focus-ring`, `--tavi-success`, `--tavi-warning`, `--tavi-danger`.
* Density: `--tavi-space-1` through `--tavi-space-6`, `--tavi-roster-row-height`, and `--tavi-touch-target` (at least 44 CSS px for touch layouts; compact desktop may use tighter rows with keyboard support).
* Typography: families, 12/13/14/16/20 px semantic sizes, readable compact line heights, minimum contrast target WCAG AA (including dark mode).
* Radius, elevation, shadow, z-index groups (`shell`, `menus`, `dialogs`, `toasts`), safe-area insets, motion-reduction and keyboard focus.
* Extensions may opt into **documented** tokens via their own stylesheet; host must never inject its global CSS across the iframe isolation boundary.

== Required regression matrix

* Window sizes: Windows compact 355×630, resized 355×911, phone 320/390/430, tablet 768, larger desktop 1024–1366. Test with native insets and keyboard present where applicable.
* Navigation flows: Home → Messages → chat → Home; Home → Apps → Atrium → App Store → Home; Home → Games → Home; Home → companion → Home; any open modal → Cancel/Escape/Android Back → previous valid surface.
* Menus: File, Contacts, Actions, Tools, Help sequential switching opens exactly one; pressing Escape collapses it and restores summary focus. Keyboard tabbing, no menu clipped outside viewport.
* Contacts: one row per accepted contact, alphabetical by chosen display name with stable fallback, recent/unread/presence co-located, no contradictory `Online (0)` while an online recent contact is present. Request actions remain accessible.
* Themes: light/dark green, text contrast, status dots and focus ring, modal/menu surfaces, theme persists after restart, native desktop and Android/WebView safe areas.
* Extensions: installed/disabled/updating states correct, host Home always present, untrusted iframe remains sandboxed, no Social token leak, same-state return from extension.
* Conformance: complete Node/Python regression, `tools/generate-looprd.py --check`, compiled web client, browser fixture UI QA, ZipRunner source archive preflight. Native installers and deployed-operator acceptance not inferred from green source tests.

== Non-goals and release gates

* No LoopRD schema change, no data migration, no private repository automation, no forced local extension installer, no new game authorization contracts.
* Do not conflate source tests, ZipRunner import, exact-commit CI, native Windows/Android builds, release publication, or real UI/operator acceptance.
* Do not declare any old workboard ticket Done just because the shared framework plan exists or source tests pass.
* An eventual design system should be publishable independently as an optional extension SDK, but **never** force extensions to import privileged Tavi host code or break independent external publishers.
