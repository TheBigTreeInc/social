= Tavi: Design and Architecture
TheBigTreeInc Social project
:revnumber: 0.3.40
:toc: left
:sectnums:

== Source of truth

This AsciiDoc document is the canonical cross-client design specification for the
`looprd-social` project. Repository root `looprd.yaml` is authoritative for the
running Social API schema and actions; `server/looprd_handler.py` generates its handler.
The two documents are complementary, and **this design must not redefine LoopRD core**.

== Target boundary: Atrium owns gaming

Tavi is a *chat-first messenger*, optionally with a small phone-like app launcher.
Atrium, opened independently or via a Tavi shortcut/invitation, owns game
catalog, lobbies, game launching, and player game discovery. Games retain
rule/state authority. The previous in-Tavi Games panel and Windows game iframe
are legacy implementation details, *not* the desired product direction.
See `docs/ATRIUM_INTEGRATION.adoc` for target flows, portable registration,
security boundaries and a staged migration plan.

== Product identity and layout

Tavi is a compact, game-oriented messenger, inspired by the dense
contact-list and conversation conventions of MSN Messenger and Xfire. The desktop
shell should use a narrow contact roster, small classic menus and toolbar controls,
white message history, thin borders, and compact status indicators. Do not reintroduce
a three-column dashboard or oversized rounded panels. A conversation has simple
sender/time/text transcript lines. Mobile reuses the same data operations and
switches between roster and conversation. On Windows, the main native window MUST be a roughly 355px-wide buddy roster, not a maximized dashboard or a small login panel inside an oversized host. Conversations MUST open in independent native windows and preserve the account session through the authenticated main window.

== Mandatory client parity

Every shipped release MUST contain all of these client targets from the **same
canonical JavaScript Social API**:

[cols="1,2,2",options="header"]
|===
| Target | Source/build | Distribution
| Web browser | `client/src/` + `client/sdk/looprd-social.js` | Static `client/dist/` from `npm run web:build`; CI artifact `social-web-client`
| Windows | Same JS UI + Tauri v2 shell | GitHub Actions NSIS installer
| Android | Same JS UI + Tauri v2 shell | GitHub Actions Android APK
| Embedded JS integration | `client/sdk/looprd-social.js` | Standalone ES module at `dist/sdk/looprd-social.js`
|===

Browser and native targets MUST share protocol logic rather than copy it. A failure
in one native toolchain must not prevent generating the static web artifact. The
`web.yml` workflow validates the reusable SDK and builds independently of Rust,
Android SDK, and Tauri installer packaging.

== LoopRD server relationship

* One selected LoopRD **origin** at a time. The presence of the `looprd-social`
  component is probed at `/looprd/looprd-social/v1/info` and then `capabilities`.
* If Social is missing, the client displays Social unavailable: no fake accounts,
  locally stored chats, substitute identity provider, or automatic federation.
* Each game's activity endpoint is independently implemented by that game at the
  same LoopRD origin. Social passwords and session tokens MUST NOT be sent to games.
* LoopRD owns generic API, database, events and policy primitives. Social owns
  users, sessions, contacts, messages, profile, and developer entitlements.
  Games own turns, rooms and game state.

== Same account on every device

The account identity is assigned and persisted by the Social component on that
LoopRD server. The browser, Windows app, and Android app use the same username and
password and get *different revocable session tokens*, both pointing to the
same server-side Social account. Contact list, profile, portrait decimal-string
code and messages are server-backed and therefore shared. Social sessions
are device-specific and revocable. Tavi supports explicit "Keep me signed in"
persistence in origin-scoped browser/WebView storage (not account passwords).
Native OS-backed credential storage remains planned. Saved tokens must never
be sent to a game, URL, push payload, generated bundle or ZipRunner package.
A web client MUST require HTTPS for a non-local LoopRD origin. Production deployment
must configure the permitted browser `Origin` on the LoopRD server (CORS).

== Client features

* Registered account discovery, sign-up, sign-in, current profile, and sign-out.
* Online/offline buddy roster, requests/acceptance, DMs and public community lobby.
* Game activity and foreground turn notifications where a game publishes its
  optional `looprd.game.activity/v1` response.
* Portrait library: verified official online metadata/artwork and reviewed,
  pinned executable renderer source. Store canonical portrait code as **text**.
* Optional server-granted developer mode (a per-account database flag, default
  false). The UI setting appears only for a permitted account; diagnostics
  requests are independently authorized by Social on every call.

== Privacy, trust and failure states

Social exposes no master LoopRD management credential. Browser static builds
contain no configured account, token, database, private key, or server-specific
secret. HTML messages are escaped. An offline/unreachable server does not
trigger a local-account fallback. A missing game activity endpoint does not
break messaging. Revoke only the requesting device session on sign-out.

== Versioned design maintenance rule

For **every** client change affecting layouts, APIs, account/session behavior,
capabilities, or deployment: update this `.adoc` and
`docs/JAVASCRIPT_CLIENT.adoc` where applicable, test the JavaScript SDK, and
verify that `web.yml`, `windows.yml`, and `android.yml` remain maintained.
The ZipRunner Work board must mention changes to these contracts. Do not
consider a release complete unless static-web and SDK artifact checks pass;
Windows/Android installer and physical-device acceptance remain separate gates.

== Deployment and outstanding limitations

`npm run web:build` from `client/` produces static `dist/` and an independent
`dist/sdk/looprd-social.js` ES module. Serve the contents of `dist/` on HTTPS
(or localhost for development); nested hosting paths are supported by relative
asset paths. No Node service or Tauri shell is needed to host it.

Web push while the browser is closed, terminated Android push, recovery, abuse
controls and native independent chat windows are not implemented here. An
upstream LoopRD component must actually activate the Social database schema
before register/login can succeed; ZipRunner source installation alone does
not activate or migrate the live backend.

== Native Windows window geometry (v0.3.8)

* Sign-in and buddy list are the *entire* native window, initially 355 x 630 logical pixels. The main window stays narrow; the desktop window decoration is provided by Windows, without a duplicate simulated caption. Do not fill a 1060-pixel shell with blue whitespace.
* Selecting a contact or Community Lobby opens or focuses a separate 585 x 525 conversation window. Each conversation has its own message history and composer. Multiple windows may coexist.
* The main window brokers authenticated Social requests over application-scoped Tauri events; credentials MUST stay in its process memory and MUST NOT be included in a chat-window URL, browser storage or an event payload. Social authorizes each private message at the server. Closing/signing out of the roster ends access to those sessions.
* Settings, Games, and Portrait screens temporarily replace the roster in the narrow main window; Back to contacts restores the roster. Allow scrolling where required.
* Browser remains a separately shipped HTML/JS build. Android remains single-window responsive navigation; do not open desktop popup webviews on phones.
* Acceptance MUST verify actual native window dimensions and independent conversations in Windows Actions; HTML source checks alone cannot certify OS behavior.

== Tavi identity and friend discovery (v0.3.5)

Tavi is the user-facing name. `looprd-social`, its HTTP paths, database, and account IDs remain unchanged. All Windows, Android and browser clients use the same Social account on a chosen home server.

=== Registration and contact UX

* Registration errors appear inline beside the account form; never rely on a transient toast.
* Username is 3–24 lowercase letters, digits or underscores and begins with a letter; password is 12–128 characters.
* Adding a friend is a dedicated, keyboard-accessible form, not a JavaScript prompt.
* Contact requests require acceptance before private messaging.

=== Federation architecture (design only; not implemented)

A Tavi identity has one home server. Remote identities use `username@host`, but do not interpret a remote address as a local username. Social owns remote discovery, relationships, blocking and message semantics; LoopRD core provides generic HTTP, persistent delivery queues and verified server-to-server credentials. No global identity directory is required.

Phase 1: verified HTTPS discovery document and signed server identity with explicit trust configuration. Phase 2: signed, replay-protected request/accept/reject friend invitations with consent and per-server rate limiting. Phase 3: durable idempotent message delivery and acknowledgement with retry queues. Phase 4: presence with privacy controls, blocking, key rotation, migration and abuse handling.

Do not allow arbitrary remote URL fetching from client-supplied addresses (SSRF). Never trust unsigned remote claims, never replicate password hashes or session tokens, and do not treat federation as implemented until end-to-end tests across two independent servers pass.

== Legacy: promoted games and the player window (0.3.8)

NOTE: The following section describes currently shipped/historical functionality and is superseded as target design by `docs/ATRIUM_INTEGRATION.adoc`. Do not extend this model for new games.

* Social handles `game_catalog` with a public read-only `tavi.game-catalog/v1` response. The operator sets `TAVI_GAME_CATALOG_JSON` to an array of reviewed `id`, `name`, `url`, `embedded` entries; empty by default. Only public HTTPS URLs without credentials, fragments or local-network hosts are accepted. The server is authoritative; no client may publish its own game.
* Windows opens a separate local `game.html` webview for an operator-promoted `embedded` web game, leaving Tavi's compact roster active. A sandboxed external game iframe is a display surface only. It receives no Social token or Tauri API. The local player uses an event broker in the main authenticated webview for shared server lobby feed/send only.
* Chat is the existing **community lobby**, not a game room; no claim of interoperable Life chat, SSO, join tickets, or direct messages from within the game. Those require explicit contract work.
* Browsers and Android currently open promoted games externally; native player is Windows-only. Framing can be refused by the game via CSP `frame-ancestors` or `X-Frame-Options`. Browser opening remains fallback. Some games require separate cookies and login.
* Server catalog entries do not confer privileged client capabilities; executing native binaries, native overlays, game room invitations, and federation remain workboard items.
* Maintain independent Windows NSIS, Android and web verification. No private credentials are included in game URLs, client messages or ZipRunner archives.

== Tavi branding and build experience

The product is **Tavi**, published by **The Big Tree Inc**. The implementation retains the stable `looprd-social` project key, server component and package identifiers while the user-facing windows and title use Tavi. Retro messenger styling is an interaction reference, not a borrowed identity: Tavi should develop its own coherent iconography, accessible presence cues, and distinctive palette. Local Windows installation builds are default ZipRunner build outcomes; publication to GitHub is independent and reserved for explicit source/server deployment decisions.

== Tavi v0.3.18 — server-backed message summaries

`looprd-social` schema 5 adds account-scoped, monotonically advancing DM read
markers and one authenticated summary operation across accepted contacts.
The roster orders recent conversations; Windows native companion chat windows
continue to broker actions through the main credential-bearing window.
See `docs/CONVERSATION_SYNC.adoc` for the wire contract and rollout.
Android background push and native notification action responses remain future
work; there are no new permanent administration panels.

== Push delivery portability (client readiness v0.3.19)

Tavi keeps Social chat and read status authoritative on its selected LoopRD server. Foreground Windows/Android/Web notifications use existing OS integrations. The current client adds a scoped, default-off preference for background delivery and reports readiness only when explicit Social push capabilities and native distributor support exist. Android UnifiedPush with optional self-hosted ntfy is the intended primary provider, not Firebase. An Android bridge eventually forwards only an opaque wakeup to the authenticated client; it must fetch messages from Social. No registration endpoints or subscription tokens are fabricated in this release. See `docs/PUSH_TRANSPORT.adoc` for proposed contracts and acceptance.

== Verified Social identities and background push (0.3.20)

LoopRD Social uses `auth.mode: verified`, an app-local verifier and a public,
nonprivileged registration/login guest marker; authenticated sessions are
bound to individual LoopRD principals in realm `tavi-social`. All device,
WebSocket and scoped event requests use verified bearer credentials, and
browsers obtain single-use WebSocket tickets rather than placing Social tokens
in URLs. Durable opaque pulse events and recipient-specific `ctx.notify`
wake jobs are committed with Social account/DM changes where supported.
The external ntfy provider and native Android UnifiedPush receiver are
separate deployment/device concerns, not built-in magic. See
`docs/PUSH_TRANSPORT.adoc` for exact LoopRD routes, operation requirements,
limitations and release acceptance.


== Ecosystem administrator event delivery (0.3.23)

LoopRD admission and the protected operator workspace remain the only administration
surface. The Social component explicitly exposes a safe `accounts` management
resource and named promote/revoke actions; new accounts have `ecosystemAdmin=false`.
The operator management credential MUST NEVER enter Tavi client code or a service
contract. A user's role allows eligible Tavi inbox delivery, not arbitrary API access.

Approved, privately credentialed LoopRD machine principals can publish scoped
administrator events using the declared `tavi-admin-notify` service contract and
read current Tavi-admin entitlement through `tavi-admin-role`. Their credentials
are mounted references, not a client flag. Social resolves actual recipients and
uses one transactional event and push outbox. On revocation, previously delivered
service-origin events become inaccessible and no longer actionable on the Social
API. The Inbox is dynamic, not an always-visible administration screen. Details
and operator acceptance: `docs/ECOSYSTEM_ADMIN.adoc`.

== Windows secure remembered-device credential storage (v0.3.23)

* The native Windows main window alone can read and write an OS-account-scoped, Windows DPAPI-protected session file in Tavi local application data; no plaintext Social token remains in localStorage after successful migration.
* An invalid server session is discarded only on confirmed authorization rejection or local expiration. Offline startup preserves the encrypted record for a later retry.
* Browser and Android retain their existing WebView-backed storage until dedicated platform credential adapters are implemented.
* Session storage failures are visible; a successful login is not relabeled a registration failure. Signing out clears the local credential and requests server revocation.
* Compact Settings remain scrollable and show optional notification controls in collapsible sections, with no always-visible administration panel.

== Windows rebuild lifecycle (v0.3.24)

ZipRunner builds must stop only the exact running Tauri binary in the project `target/release` path before Rust overwrites it. Stop is a best-effort graceful window close followed by forceful termination of only that verified PID. Existing installed Tavi clients at other paths are not forcibly stopped. Do not remove compiled artifacts, local state or earlier working NSIS installers as a workaround. The Windows build acceptance check must confirm real behavior and test DPAPI session persistence.

== Resilient device sign-in (v0.3.34)

The classic narrow Windows roster remains unchanged. A remembered Windows session
uses only the DPAPI-protected per-user app-data record. If the LoopRD host is
temporarily unavailable, the login screen offers an inline Retry saved sign-in and
an explicit Use another account action; bounded automatic recovery starts on
network restoration and applies exponential backoff while offline. HTTP 401 is
credential rejection; HTTP 403 is not grounds to erase a device's credential.
No local fake/offline account is fabricated. See `docs/SESSION_RECOVERY.adoc`.

== Game notifications (source candidate 0.3.40)

The Social component, not Tavi client, owns per-recipient game turn alerts. Only approved game component service identities can call `tavi-game-event/v1`; a Social user must explicitly opt into an approved game and match before service delivery. Social transactionally stores the inbox event, durable pulse and optional content-free push hint. Tavi only renders the existing inbox and safe Atrium shortcut. Atrium lobbies and Life game-seat authorization remain outside this component. This partial implementation does not grant game-scoped actor credentials or implement game invitations; see `docs/GAME_EVENT_IMPLEMENTATION.adoc`.
