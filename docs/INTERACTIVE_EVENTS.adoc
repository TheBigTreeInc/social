= Tavi Interactive Events v0.3.15

== Implemented

The Social component stores recipient-scoped events (`SocialInteraction`, schema 4). The Social API supports `interaction_feed`, `interaction_reply`, and `interaction_publish`. Publication is limited to Social developer-enabled accounts; this is an interim publisher gate, *not* LoopRD administrative role inheritance. Replies are validated server-side, expire, and cannot be repeated. Native forms support select/text/textarea. Safe outbound HTTPS URLs open externally without passing the Social token. Tavi does not add a persistent admin section.

== Deliberately not implemented

Role-driven admin subscriptions, third-party authenticated publication, scoped pre-authenticated web panels, external panel origin registration, and cross-server event federation need DAPI/LoopRD specification and runtime support. `native-webview` is declarative metadata only in this release and falls back to the external browser, not a privileged embedded pane. There is no impersonation or silent approval.

== Admin test interaction

Use an existing developer-enabled Social account and issue `interaction_publish` to a *local* account handle. `interaction` requires `topic`, `title`, `body`, and an `actions` array with `id`, `label`, `type=reply|open-url` and appropriate fields/URL. Supply `ttlSeconds` between 60 and 604800. To view, log in as the recipient and open Inbox. Replies return a response record tied to the authenticated recipient. Never put administrator management credentials in Tavi.

== Server deployment

This pass changes `looprd.yaml`, the handler and schema version 3 to 4. A source publication and managed LoopRD component reload are required, unlike client-only releases. Back up the component DB and check migration before activating.

== Inbox lifecycle (0.3.16)

The recipient may dismiss an open interaction via `interaction_dismiss`. The server checks session identity, ownership, and state; dismissal is idempotent for that recipient and prevents later reply. The client separates actionable and historical events without installing a permanent admin screen. The component database schema remains 4; status is stored in the existing status column.

== LoopRD role and service delivery (0.3.23)

LoopRD `management.data` now allows the operator to promote/demote existing Tavi
accounts through the protected Data & actions workspace. Tavi `ecosystemAdmin`
controls whether a user can receive or act on events issued by approved machine
service principals. The `tavi-admin-notify` and `tavi-admin-role` service contracts
provide explicitly authorized cross-component integration. Notification writes and
content-free push hints are transactional; role revocation immediately hides
service-origin events and denies responses. See `docs/ECOSYSTEM_ADMIN.adoc`.

A LoopRD management key is NOT a client admin identity. No generic LoopRD-wide
role directory, third-party SSO, arbitrary admin database operations, or embedded
origin-bound privileged web panel is implemented. HTTPS links open externally.
