== Tavi 0.3.119 — Exact-file-gated ZipRunner review

The operator requests a manually supplied ZipRunner extension that works only after the existing web-connection authentication file is sideloaded inside Tavi. The review app is included in the internal registry as optional, with a separate package for manual distribution. Its assets are mirrored through the normal integrity-checked extension sync; it is never installed/enabled automatically. The exact extension inc.thebigtree.ziprunner.review may request the application-specific ziprunner.review permission. Its host bridge accepts bounded original v2 .zrmobile bytes, computes the exact SHA-256, validates one HTTPS origin and expiry, and asks that issuer for sanitized read-only review using the secret and file digest on every request. No browser/Tavi login, cookie or generic API token substitutes for the file.

Credentials remain in per-frame/session memory only, never storage, logs, URLs or source. Mount/unmount, account/frame change, clear, expiry, rejection or revocation discard the grant. Generation checks reject late asynchronous responses. Requests omit cookies, reject redirects and use fixed read-only review/project routes; no generic networking, native/file access, commands, builds, configuration, Git, publishing or release actions are exposed. Preserve the extension iframe sandbox and existing CSP. Only the bundled, integrity-verified app source is eligible; remote lookalikes, other IDs/frames or missing permissions are denied. The module is advertised only to the exact authorized application. Older hosts reject the new permission or fail closed on feature negotiation.

Context: the existing host intentionally denies extension networking; enabling arbitrary iframe fetches would weaken that boundary. Reuse the existing ZipRunner-issued credential format and add a narrow host broker rather than a second login or general network permission. Source-only rollback removes the optional bridge without changing accounts, saved extensions, Social/Wallet data, configuration or existing authorization. Manual Tavi/extension installation and operator Windows/Android acceptance remain separate gates. Governing work: TAVI-ZR-REVIEW-001; paired ZipRunner work: ZR-TAVI-001.

== ADR TAVI-SHARED-0141 — Account-scoped host service capability parity

=== Context and decision

Governing source review: `docs/TAVI_SHARED_SERVICES_COMPATIBILITY_0141.adoc`.
Atrium 0.5.77 consumes the TaviX 0.1.10 proposed installed-games contract; Social 0.3.140 had no host implementation. Assets 0.1.7 adds portable discovery/composition methods outside Social's eight-method host adapter. Reuse the existing TaviX 1.0 `host.info` feature negotiation instead of inventing a second unscoped server gateway. Only an active official Atrium frame can read an immutable DTO of the currently approved, installed, compatible classified games and request a host-controlled open. The signed-in Social account and locally reviewed source/version are rechecked before navigation. Assets grants remain explicitly default-denied until a real trusted storage/entitlement/runtime integration is approved.

=== Alternatives and risk

Direct Atrium access to local extension storage or the Social auth token was rejected. A generic all-extension game listing was rejected. Directly launching iframe-supplied URLs was rejected. Reimplementing Assets engine and entitlement logic within Social was rejected. Publisher-hosted executable code is still mutable unless independently content-pinned; a reviewed catalog revision does not prove immutable remote bytes. Keep remote publisher trust explicitly visible in operator acceptance, and preserve child-safe messaging by never exposing general private contacts, messages, wallet or game-authority methods through this bounded pass.

=== Compatibility, release and rollback

No private state migration or new server endpoint. Host SDK adds optional methods while `tavi.extension/v1` and version 1.0.0 remain unchanged. Installed game classification and registered game launching work on desktop, Android and web with the same source rules; real native acceptance remains an operator gate. Revert the optional host modules/entry points to restore 0.3.140; no stored game state or server schema changes are required. Release, Git push and deployment are separate approved operations.

== ADR TAVI-ASSETS-STORE-0143 — First-party storefront with explicit host consent

=== Context and decision

Governing implementation: `docs/TAVI_ASSETS_STORE_0143.adoc` and previous
`docs/TAVI_TAVIX_ASSETS_RUNTIME_0142.adoc`. The 0.3.142 proof of concept relied
on JavaScript `confirm()` dialogs which cannot fit or resize reliably in the
355x630 native shell. Move bundled pack discovery and account-local management
into a first-party store surface. Keep the asset engine, persistence and
TaviX 0.1.11 grant checks unchanged. Only first-party click handlers can install
or approve; no extension message may initiate these privileged actions.

=== Catalog and trust boundary

A build-configured HTTPS `tavi.assets.catalog/v1` catalog may display bounded
metadata via a credential-free, no-redirect request. It never authorizes an
installation, purchase or entitlement. No official Assets URL has been supplied,
so the default build is explicitly offline. Full remote pack delivery is blocked
pending an approved immutable package distribution/authorization contract from
Tavi Assets and LoopRD/Wallet, not guessed from the App Store or TaviX registry.

=== Alternatives, migration, rollback

Browser-native dialogs, generic extension network permissions and automatically
installing packs from untrusted catalog URLs were rejected. This update adds no
server route or persistent data schema and preserves existing installed packs,
versions, app grants and settings. Rollback removes the first-party storefront
and restores the previous Settings entry without touching user data. Native
Windows/Android rendering and operator acceptance remain mandatory.

== ADR TAVI-WIN-DIAG-0163 — Native client fail-visible startup classification

=== Context and decision

An operator screenshot of the exact 0.3.162 Windows package shows the 0.3.162 guard's `TAVI_STARTUP_SCRIPT_ERROR` fallback, not the messenger Home. The guard's global captured `error` handler also classified unrelated failed images/icons as a *script* failure, so that code is insufficient evidence of the native cause. Preserve the existing pre-module, credential-free classic bootstrap, but classify module resource failures, runtime exceptions, promise rejections, first-render timeouts, and missing-module timeouts distinctly. The first-party main module marks its execution start and successful first render. Only the safe type, same-origin asset basename and bounded line/column are shown; raw error messages, full URLs, query strings, credentials and stored account state are excluded.

=== Scope, alternatives, rollback and release

This is diagnostic instrumentation, not a fix for the underlying 0.3.161/0.3.162 native startup failure. Avoid WebView2 developer bypasses, storage resets, special dev mode or weaker extension sandbox. An extracted source test can verify classification but cannot prove installed Windows WebView2 behavior. Physical Windows console/network evidence and a successful messenger render remain hard operator gates. Revert the new boot guard and optional progress hook to return to the 0.3.162 generic fallback; no account or server data migration is involved. Governing work: `TAVI-WIN-BLANK-162`.

== ADR TAVI-WIN-TDZ-0164 — Defer desktop workspace notification binding

=== Context

On the installed Windows client 0.3.163 the operator observed `TAVI_STARTUP_RUNTIME_ERROR ReferenceError` in the main application bundle before Tavi rendered. Source review traced a reproducible premature lexical binding to the original 0.3.161 workspace implementation: `createNativeWorkspaceManager` was passed `notify:toast` while the later `const toast` declaration was still in JavaScript's temporal dead zone. This initializer only executes when `nativeDesktop` is true, explaining why desktop behavior differs from mobile. The observed minified bundle coordinate is not source-mapped here, so native causality still requires acceptance.

=== Decision

Bind `notify:message=>toast(message)` instead. The callback closes over the same `toast` variable, but the reference is evaluated only after initialization when a detached-window failure must be displayed. All TaviX sandbox, authorization, lifecycle and server contracts stay unchanged. Do not change UI/UX design tokens, use storage resets, or circumvent native builds to make the issue disappear.

=== Verification and rollback

`client/tests/windows-startup-tdz-164.test.mjs` executes the actual callback expression in a simulated pre-initialization desktop environment and asserts that the message is delivered after the `toast` declaration. The old eager expression throws a `ReferenceError` under the same test. Node source checks do not prove that Windows WebView2 renders; the operator must build/install the exact ZIP and verify messenger Home, session retention, detached workspace and notification. Rollback is a source-only reversion, though the earlier eager binding must not be reintroduced. Governing work: `TAVI-WIN-TDZ-164` (review) and `TAVI-WIN-BLANK-162` (remaining until native acceptance).

== ADR TAVI-WORKSPACE-CLOSE-0168 — Native application close follows Tauri ACL

=== Context and decision

Governing contract: `docs/TAVI_WORKSPACE_CLOSE_REPAIR_0168.adoc`.
0.3.167 detached TaviX windows were unable to complete Return to Tavi because the main window lacked Tauri `core:window:allow-close`; errors were swallowed after disposing the authenticated relay. Grant only the native close permission to the main broker and isolated workspace shell. Keep the sandboxed TaviX iframe unprivileged; provide Close window in the shell. Only record embedded preference and reattach after successful native close. For a rejected close, retain the relay and preference and display a sanitized error.

=== Alternatives, migration and rollback

Unrestricted `core:window:allow-destroy`, exposing raw Tauri commands to TaviX, forcing process termination, and automatically resetting app state were rejected. The change adds no persistent data schema, new server API, general native permission or credential flow. Reverting the close repair restores the former broken behavior; preserve local preferences and user state. Exact native Windows close/return/Alt+F4 acceptance and operator approval are required separately from JavaScript source tests.

== ADR TAVI-WORKSPACE-CLOSE-0169 — Do not intercept native close for cleanup

Governing corrective specification: `docs/TAVI_WORKSPACE_CLOSE_REPAIR_0169.adoc`. The 0.3.168 `onCloseRequested` listener intercepts Windows native close and requires Tauri `Window.destroy` permission to finish. Remove that listener, keep `allow-destroy` denied, observe only Rust `WindowEvent::Destroyed` for verified workspace labels and ask the main broker to verify native absence before disposing the scoped SDK relay. Windows operator verification is still required before acceptance.
