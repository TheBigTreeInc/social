= Wallet extension-owned backend embedded in LoopRD Social
:toc:

== Deployed topology

Tavi is a messenger and optional extension host. The first-party *Wallet* is a permanent core extension. Its **canonical backend source** is now `wallet_ledger.py` in this directory, not `server/wallet_ledger.py`.

`tools/generate-looprd.py` reads this file and the reviewed `backend.json` contract and embeds the *same Wallet implementation* into the existing `looprd-social` component's `/wallet`, `/ecosystem/wallet-merchant`, and `/ecosystem/wallet-reward` routes. The descriptor still declares realm `tavi-social`, Social's verified principal and SQLite schema 11. This source ownership change **does not** create or register a second component, change a route, require an account migration, or move Gold/transaction tables. A LoopRD instance can host both Social and Wallet responsibilities as one deployed component.

This is a source/module extraction within the same LoopRD instance. It does **not** claim deployment of the future separately importable Ledger service (workboard `TAVI-WALLET-SPLIT-082` remains planned). No additional registry authority, server URL, credentials or installation step is added to the iframe.

== Operational activation

1. Back up the Social/Wallet database. Inspect the running LoopRD `looprd-social` component and its schema before making changes. Never replace its storage with local development state.
2. If the live component is still before schema 11, reconcile the operator-approved existing `looprd.yaml` **once** against the supported LoopRD runtime (tested 10 -> 11 migration). A schema 12+ instance needs its own reviewed migration path; do not downgrade it to 11.
3. Verify a signed-in ordinary Tavi account may call `/wallet`, that a second account sees an isolated balance, and that service-only merchant/reward routes reject ordinary clients.
4. Verify a first balance read creates at most one free welcome credit, balance persists across restart, free Gold cannot purchase shop items or be converted, and replayed requests return existing receipts.
5. Only approved game merchants may fulfill orders or issue bounded rewards. No client-side minting, paid Gold, cash-out, wagering, or real-money exchange.
6. Windows/Android/Web native Wallet and GitHub exact-SHA CI must pass before operator approval. No automatic push/release/deploy from ZipRunner package.

== Source and artifact invariants

* `extensions/org.tavi.core.wallet/looprd/wallet_ledger.py` is canonical and private server code.
* `server/wallet_ledger.py` is a small legacy import-only adapter to avoid leaving stale old logic under ZipRunner's `delete_missing=false` overlay policy; it never defines Wallet operations and is not embedded in LoopRD.
* The generated `looprd.yaml` must match `python tools/generate-looprd.py --check` exactly.
* `extensions/.../looprd/` is excluded from the public static App Store mirror.
* `extensions/registry.json` keeps backend component `looprd-social`; `backend.json` asserts this contract during generation.
* WalletBalance, WalletTransaction, WalletEntry, WalletOrder, WalletRestrictedBalance and WalletRewardIssue retain their original table names and data on the existing database. No destructive migration.
